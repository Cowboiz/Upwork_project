# User Flows

> Version: v0.1  
> Goal: Keep every early flow short enough to operate manually and measurable enough to validate the marketplace.

## Flow Principles

- Prefer short, manually verifiable flows for the MVP.
- Avoid building automation before the manual version proves useful.
- Capture enough information to match users without making onboarding feel heavy.
- Always make the next step and expected response time clear.
- Screen out prohibited academic-integrity requests before provider matching.
- Record why users drop, decline, cancel, or dispute whenever practical.

## Student Request Flow

1. Student arrives from an acquisition channel.
2. Student reviews the basic offer, expected process, and prohibited-work policy.
3. Student submits project details and confirms the request is legitimate.
4. Operator reviews request for clarity, fit, budget, deadline, and policy compliance.
5. If needed, operator asks one round of clarification.
6. Operator identifies 1–3 suitable providers.
7. Operator confirms provider interest and availability.
8. Operator proposes the provider(s) or next step to the student.
9. Student accepts, declines, or asks questions.
10. If accepted, scope, price, timeline, delivery method, and revision expectations are written down.
11. Work begins.
12. Outcome, payment, completion, feedback, referral, repeat intent, or dispute is tracked.

### Required Inputs

- **Name:** Required.
- **Contact method:** Required; one reliable channel.
- **School or context:** Optional; collect only when useful for validation or trust.
- **Project type:** Required; choose from initial categories plus “Other”.
- **Deadline:** Required; allow “flexible”.
- **Budget range:** Required.
- **Description:** Required; prompt for goal, deliverables, existing assets, and constraints.
- **Relevant files or links:** Optional.
- **Acquisition source:** Required or automatically captured.
- **Academic-integrity confirmation:** Required.
- **Permission to contact:** Required.

### Drop-Off Risks

- **Form is too long:** Keep the first form to the information needed for a match; ask follow-up questions manually.
- **Trust is unclear:** Explain provider review, privacy, response time, and what happens after submission.
- **Pricing is unclear:** Show budget bands and explain that final price depends on scope.
- **Timeline feels uncertain:** State the target first-response and shortlist time.
- **User worries about spam:** Explain that contact details are private and not publicly listed.
- **Student wants prohibited work:** Politely reject and, when appropriate, redirect to allowed tutoring, feedback, or learning support.

## Provider Onboarding Flow

1. Provider arrives from outreach, community, or referral.
2. Provider reviews the type of projects, expectations, and prohibited-work policy.
3. Provider submits profile and skill information.
4. Operator reviews identity signals, portfolio quality, communication quality, skills, and project fit.
5. Provider is accepted, rejected, or waitlisted.
6. Approved provider receives matching expectations and response-time guidance.
7. Provider receives only relevant opportunities.
8. Provider accepts, declines, or asks for clarification.
9. Operator records response and availability.

### Required Inputs

- **Name/display name:** Required.
- **Contact method:** Required; kept private unless both sides agree to connect.
- **Skills:** Required; structured tags plus optional notes.
- **Portfolio links:** Required; at least one demonstrable example.
- **Availability:** Required; current weekly capacity or next available date.
- **Preferred project types:** Required.
- **Rate expectations:** Required as a range or minimum project value.
- **Location/time zone:** Optional unless needed for coordination.
- **Acquisition source/referrer:** Required or captured.
- **Agreement to prohibited-work policy:** Required.

### Provider Review Criteria

- Portfolio demonstrates the claimed skill.
- Communication is clear enough for client work.
- Rate expectations fit the pilot categories.
- Availability is current.
- No signs of impersonation, copied portfolio work, or prohibited services.

## Manual Matching Flow

1. Operator reviews a qualified student request.
2. Operator filters approved providers by project type, skill, budget fit, availability, and past outcomes.
3. Operator selects up to 3 candidates.
4. Operator sends a concise opportunity brief to candidate providers.
5. Provider accepts, declines, or requests clarification.
6. Operator records response time and decline reason.
7. Operator presents the strongest available option(s) to the student.
8. Student selects a provider or declines.
9. Operator records the match result.
10. If no match is found within 48 hours, operator records the reason: price, skills, deadline, availability, quality, or other.

## Project Completion Flow

1. Student and provider agree in writing on:
   - Deliverables.
   - Price.
   - Deadline/milestones.
   - Number of revisions or change process.
   - Delivery format.
2. Work begins.
3. Operator checks status only when needed; do not turn the MVP into a project-management service.
4. Work is delivered.
5. Student confirms accepted, revision requested, cancelled, or disputed.
6. Payment state is recorded.
7. Student and provider give short feedback.
8. Operator records:
   - Final price.
   - Completion date.
   - Quality outcome.
   - Dispute/refund if any.
   - Repeat intent.
   - Referral.
9. Learning is added to the decision/roadmap documents if it changes a product or business assumption.

## Admin Flow

### Review new student requests

- Open New requests.
- Check policy compliance.
- Check whether brief, budget, and deadline are matchable.
- Clarify once if needed.
- Mark Reviewed or Cancelled/Rejected with reason.

### Review new provider applications

- Review portfolio and skills.
- Check rate/budget fit.
- Check availability.
- Approve, waitlist, reject, or mark inactive.

### Track matches

- Create candidate match.
- Send opportunity.
- Record provider response.
- Record student decision.
- Track accepted match.

### Track conversion

Monitor:

- Request → reviewed.
- Reviewed → viable candidate.
- Candidate → accepted match.
- Match → paid.
- Paid → completed.
- Completed → repeat/referral.

### Track project outcomes

Record:

- Delivered on time?
- Student satisfied?
- Provider satisfied?
- Final price?
- Dispute/refund?
- Reason for failure if not completed?

### Capture qualitative feedback

After completion or failure, ask one or two questions:

- “What was the hardest part of this process?”
- “Would you use this again? Why or why not?”
- “What would have made this easier?”

## Exception Flows

### Prohibited Academic Work

1. Request appears to involve graded coursework, an exam, take-home assessment, or impersonation.
2. Operator pauses matching.
3. Operator asks for clarification if genuinely ambiguous.
4. If prohibited, request is rejected.
5. If possible, student is redirected to allowed tutoring, conceptual explanation, debugging, feedback, or learning support.

### No Provider Available

1. Record reason.
2. Tell student quickly.
3. Offer revised scope/budget/deadline only if reasonable.
4. Do not send irrelevant providers just to create a “match”.

### Dispute

1. Pause status as Disputed.
2. Preserve scope, messages/notes, delivery evidence, and payment status.
3. Avoid making promises before reviewing facts.
4. Follow documented refund/payment-provider process if applicable.
5. Record resolution and root cause.
